# 02. Database Schema

One PostgreSQL database (`visa_management`), one schema per service. The full DDL lives in `infrastructure/postgres/init.sql` — this document explains the **why** behind each table.

## Schema map

| Schema | Owner Service | Purpose |
|---|---|---|
| `auth` | auth-service | Credentials, refresh tokens, login audit |
| `users` | user-service | Users, personas, offices, reference data |
| `requests` | request-service | Visa requests + beneficiaries |
| `workflow` | workflow-service | Transitions + immutable audit log |
| `documents` | document-service | File metadata (bytes in MinIO) |
| `notifications` | notification-service | Email queue + in-app notifications |
| `reporting` | reporting-service | Pre-aggregated metrics (Phase 2) |

## Cross-schema reference policy

> **Rule:** No foreign keys cross schema boundaries.

This is deliberate. Cross-schema FKs would couple deployments and prevent splitting schemas into separate physical databases later. Instead:

- `requests.visa_requests.office_id` references `users.offices.id` by **value only** (UUID).
- Integrity is enforced at the application layer (request-service calls user-service to validate the office exists at creation time, then trusts the UUID).
- Audit log records the resolved name at write time so historical reports don't break if the office is renamed.

## auth schema

### `auth.credentials`
Stores password hashes — never plaintext. `user_id` is the same UUID used in `users.users.id`; we don't redeclare the user here, just their credential.

| Column | Notes |
|---|---|
| `user_id` (PK) | Same as `users.users.id` — provided by auth-service on user creation event |
| `email` (citext, unique) | Case-insensitive lookup |
| `password_hash` | bcrypt with cost factor 12 |
| `failed_logins`, `locked_until` | Brute-force lockout (5 attempts → 15 min lock) |
| `last_login_at`, `last_login_ip` | Surfaced to user in UI for security awareness |

### `auth.refresh_tokens`
Refresh tokens are stored **hashed** (SHA-256). The plaintext token is given to the client only once. Revocation is simply setting `revoked_at`.

### `auth.login_audit`
Every login attempt — success or failure — is recorded. Used for security investigation and the BRD's audit requirements.

## users schema

### `users.offices`
The BRD §1.1 "Offices (Request Source)". Each has bilingual names and the `authorized_person` + `telephone_number` that auto-populate on the request form (per BRD §5.2 form table).

### `users.users`
Just identity + display. Authentication lives in auth schema. `office_id` is nullable — FAD staff have no office.

### `users.personas` and `users.user_personas`
Persona model from BRD §6 — a user can have multiple personas. We seed five: OFFICE, SENIOR_ADMIN, SENIOR_OFFICER, DIRECTOR, TYPIST. Permissions live in code (not table-driven RBAC) for speed and explicitness; this is a small fixed set.

### `users.countries` and `users.visa_types`
Reference data for the dropdowns on the request form. Bilingual labels.

## requests schema

### `requests.request_status` (ENUM)
Tracking the BRD workflow precisely:
- `DRAFT` — Office user creating, not yet submitted
- `SUBMITTED` — Office submitted, awaiting initial verification
- `INITIAL_VERIFICATION` — With Senior Admin
- `FINAL_VERIFICATION` — With Senior Officer
- `DIRECTOR_REVIEW` — With Director
- `TYPIST_PROCESSING` — Director approved, Typist working
- `WAITING_FOR_EMBASSY` — Typist sent to embassy, Office uploading visas
- `WAITING_FINAL_REVIEW` — Senior Officer doing final review
- `COMPLETED` — Terminal: success
- `RETURNED_TO_OFFICE` — Sent back for correction (can re-enter SUBMITTED)
- `APOLOGIZED` — Terminal: Director closed with apology
- `REJECTED` — Terminal: rejected outright

### `requests.visa_requests`
Maps directly to BRD §5.2 form fields. `request_number` follows `VR-YYYY-NNNNNN` format generated by `requests.next_request_number()` function.

### `requests.beneficiaries`
One row per traveler. BRD requires document counts to match beneficiary counts — enforced in workflow-service when transitioning from DRAFT → SUBMITTED.

## workflow schema

### `workflow.transitions`
Every state change as an immutable row. `actor_persona` captured at write time so reports work even if user's persona assignments change later.

### `workflow.audit_events`
The compliance backbone. Captures every significant action (not just transitions — also document uploads, fee changes, email sends). Append-only:

```sql
-- Production hardening to add later:
REVOKE UPDATE, DELETE ON workflow.audit_events FROM visa_admin;
```

`payload` JSONB is structured per event type — see `04-test-cases.md` for shapes.

## documents schema

### `documents.documents`
Metadata only — actual bytes in MinIO. SHA-256 prevents silent tamper: on download we can re-compute and verify. `storage_key` follows pattern `requests/{requestId}/{documentId}/{filename}`.

Soft delete via `deleted_at` so the audit trail survives.

## notifications schema

### `notifications.emails`
Captures every email sent — even when sent via the BRD's "Actions" button. The Senior Officer / Director can audit "what did I send and when" via the request detail page.

### `notifications.in_app`
Real-time notifications: "Your request VR-2026-001047 has been approved by the Director."

## Indexes

Every FK has an index. Status + assignee indexes support the dashboard queries efficiently. Audit indexes support compliance queries by (entity, actor, time range).

## Migrations strategy

For this challenge, `init.sql` runs on container start. For production, switch to TypeORM migrations:

```bash
npm run migration:generate -- src/migrations/AddNewColumn
npm run migration:run
```

Each service owns its migrations folder; CI runs them in the right order based on schema dependencies declared in the deployment manifest.
